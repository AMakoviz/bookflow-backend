## 1. Intent

Deliver the first complete BookFlow vertical slice: a demonstration employee enters a meeting interval and participant count, sees suitable available rooms, creates a conflict-safe booking, and immediately sees it in their booking list.

The slice must be demonstrable locally, exercise the browser, layered backend, and PostgreSQL together, and provide evidence that concurrent requests cannot double-book a room.

## 2. User story and outcome

As an employee, I want to find and reserve a meeting room that fits my meeting, so that I can organize it without manual coordination or the risk of double booking.

The slice succeeds when:

- the scripted happy-path booking can be completed in less than 60 seconds;
- all specified overlap and concurrency scenarios are rejected correctly;
- a successful booking is visible immediately in the demonstration employee's booking list;
- the project starts locally through one documented Docker Compose command.

## 3. Scope

### In scope

- Seeded demonstration employee and meeting rooms.
- Search by start, end, and participant count.
- Capacity, active-room, working-hours, duration, increment, past-time, and horizon validation.
- Creation of an immediately confirmed booking.
- PostgreSQL-enforced prevention of overlapping confirmed bookings.
- Display of the demonstration employee's upcoming bookings.
- Browser states for loading, no results, success, validation error, and booking conflict.
- OpenAPI contract, automated checks, local Compose environment, and Evidence Bundle.

### Out of scope

- Authentication, authorization, registration, and user switching.
- Creating, editing, or deactivating rooms through the UI.
- Cancellation, rescheduling, recurring bookings, and approval workflows.
- Notifications, calendar integrations, analytics, and multi-tenancy.
- Deployment to a public environment.
- AI-powered product functionality.

## 5. Domain language and ownership

### Room resource

`Room` is a bookable meeting-room resource persisted in the `resource` database schema.

| Attribute | Rules |
|---|---|
| `id` | UUID, stable |
| `name` | Required, unique, human-readable |
| `location` | Required display value |
| `capacity` | Positive integer |
| `status` | `ACTIVE` or `INACTIVE` |

Room data access belongs to `RoomRepository`; room lookup and bookability checks belong to `RoomService`. Controllers never access repositories directly, and persistence entities never cross the HTTP boundary.

### Booking

`Booking` is an employee's confirmed reservation of one room for one half-open interval `[start, end)`.

| Attribute | Rules |
|---|---|
| `id` | UUID, generated by the application |
| `roomId` | UUID of an existing room |
| `employeeId` | UUID of an existing demonstration employee |
| `start` | Offset-aware instant, inclusive |
| `end` | Offset-aware instant, exclusive |
| `participantCount` | Positive integer, no greater than room capacity |
| `status` | `CONFIRMED` in this feature |
| `createdAt` | Server-generated instant |

The `booking` database schema also stores the minimal `Employee` reference data needed by this slice. This is not an authentication model. It contains `id`, `displayName`, and `email`, and has one seeded record. A future Identity feature may move that data only through an accepted SDD and ADR update.

### Layer ownership

Controllers own endpoints, handlers translate exceptions, and filters own cross-cutting servlet concerns. Service interfaces define use-case contracts; implementations under `service.impl` own orchestration and transaction boundaries. Repositories own data access, entities own persistence mappings, validators own reusable business-rule checks, MapStruct mapper interfaces translate entities to response DTOs, and configuration classes own framework wiring. Controllers return DTOs that Spring MVC serializes with Jackson and contain no room-selection or booking rules.

## 6. Business rules

The office timezone is `Europe/Moscow`.

1. `start` must be earlier than `end`.
2. The complete interval must be in the future when the command is handled.
3. Start and end must fall on the same office-local calendar date.
4. Start and end must align to a 30-minute boundary in office-local time.
5. Duration must be between 30 minutes and 4 hours, inclusive.
6. The interval must be within office-local working hours `[08:00, 22:00]`; ending exactly at 22:00 is allowed.
7. Start must be no later than 30 office-local calendar days after the current office-local date.
8. `participantCount` must be at least 1.
9. A returned or selected room must be active and have `capacity >= participantCount`.
10. A confirmed booking overlaps the requested interval when `existing.start < requested.end` and `existing.end > requested.start`.
11. Adjacent intervals do not overlap.
12. Availability search is advisory. All rules are re-evaluated when the booking is created.
13. PostgreSQL is authoritative for exclusivity when requests race.
14. Available rooms are ordered by capacity ascending, then name ascending, so the smallest suitable room appears first.
15. The booking list contains the employee's upcoming confirmed bookings ordered by start ascending.

All time-dependent rules use an injected clock so automated tests are deterministic.

## 7. HTTP contract

All endpoints use JSON under `/api/v1`, UUID identifiers, RFC 3339 timestamps with explicit offsets, and the stable problem representation from [`api-conventions.md`](../docs/engineering/api-conventions.md).

### Find available rooms

```http
GET /api/v1/rooms/availability?start=2026-10-26T10:00:00%2B03:00&end=2026-10-26T11:00:00%2B03:00&participants=4
```

Successful response: `200 OK`.

```json
{
  "rooms": [
    {
      "id": "8a8d73f1-1ef0-4e49-aef3-d84ee901a5b5",
      "name": "Focus",
      "location": "2nd floor",
      "capacity": 4
    }
  ]
}
```

Invalid interval or participant count: `400 Bad Request`.

### Create a booking

```http
POST /api/v1/bookings
Content-Type: application/json
```

```json
{
  "roomId": "8a8d73f1-1ef0-4e49-aef3-d84ee901a5b5",
  "employeeId": "3ceebbd9-84e9-40df-8123-b93128f79ac5",
  "start": "2026-10-26T10:00:00+03:00",
  "end": "2026-10-26T11:00:00+03:00",
  "participantCount": 4
}
```

Successful response: `201 Created` with `Location: /api/v1/bookings/{bookingId}`.

```json
{
  "id": "f4bed67a-185c-4978-b02e-ade43eeec5b9",
  "room": {
    "id": "8a8d73f1-1ef0-4e49-aef3-d84ee901a5b5",
    "name": "Focus",
    "location": "2nd floor"
  },
  "employeeId": "3ceebbd9-84e9-40df-8123-b93128f79ac5",
  "start": "2026-10-26T10:00:00+03:00",
  "end": "2026-10-26T11:00:00+03:00",
  "participantCount": 4,
  "status": "CONFIRMED",
  "createdAt": "2026-10-25T12:00:00Z"
}
```

Outcomes:

- invalid input or domain rule violation: `400 Bad Request`;
- employee or room does not exist: `404 Not Found`;
- room is inactive: `400 Bad Request` with code `ROOM_NOT_BOOKABLE`;
- insufficient room capacity: `400 Bad Request` with code `ROOM_CAPACITY_EXCEEDED`;
- overlapping booking, including a database-detected race: `409 Conflict` with code `BOOKING_CONFLICT`.

### List the demonstration employee's bookings

```http
GET /api/v1/employees/{employeeId}/bookings
```

Successful response: `200 OK`.

```json
{
  "bookings": [
    {
      "id": "f4bed67a-185c-4978-b02e-ade43eeec5b9",
      "room": {
        "id": "8a8d73f1-1ef0-4e49-aef3-d84ee901a5b5",
        "name": "Focus",

      "end": "2026-10-26T11:00:00+03:00",
      "participantCount": 4,

    }

```

Unknown employee: `404 Not Found`.

### Problem example

```json
{
  "type": "https://bookflow.local/problems/booking-conflict",
  "title": "Room is no longer available",
  "status": 409,
  "detail": "The room has already been booked for part of the requested interval.",
  "instance": "/api/v1/bookings",

```

The OpenAPI document is generated from or verified against these contracts. Transport DTOs remain separate from domain and persistence objects.

## 8. Persistence design

One PostgreSQL database uses separate `resource` and `booking` schemas to make table ownership visible.

### `resource.rooms`

| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | primary key |
| `name` | `varchar(120)` | required, unique |
| `location` | `varchar(160)` | required |
| `capacity` | `integer` | required, `capacity > 0` |
| `status` | `varchar(20)` | required, checked enum |
| `created_at` | `timestamptz` | required |
| `updated_at` | `timestamptz` | required |

### `booking.employees`

| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | primary key |
| `display_name` | `varchar(160)` | required |
| `email` | `varchar(254)` | required, unique |
| `created_at` | `timestamptz` | required |

### `booking.bookings`

| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | primary key |
| `room_id` | `uuid` | required, foreign key to `resource.rooms(id)` |
| `employee_id` | `uuid` | required, foreign key to `booking.employees(id)` |
| `start_at` | `timestamptz` | required |
| `end_at` | `timestamptz` | required, `end_at > start_at` |
| `participant_count` | `integer` | required, `participant_count > 0` |
| `status` | `varchar(20)` | required, checked enum |
| `created_at` | `timestamptz` | required |

The initial migration must:

- create both schemas and all tables through Flyway;
- enable `btree_gist`;
- name all keys and check constraints explicitly;
- add a named exclusion constraint on confirmed bookings equivalent to `room_id WITH =` plus `tstzrange(start_at, end_at, '[)') WITH &&`;
- add indexes for availability lookup and employee booking-list ordering;
- seed one employee and at least three active rooms with different capacities;
- use stable seed UUIDs so the demonstration configuration and tests are reproducible.

The application first performs a friendly overlap check. A violation of the named exclusion constraint is translated to the same `BOOKING_CONFLICT` result. No read-then-insert sequence is considered sufficient on its own.

## 9. Application services and persistence

### Booking service operations

- `findAvailableRooms`: validates the search interval, loads active capacity-matching rooms, removes rooms with overlapping confirmed bookings, and returns the ordered entities for response mapping.
- `createBooking`: validates the interval, employee, selected room, and capacity, performs the advisory overlap check, persists the confirmed booking in one transaction, and translates a database exclusivity violation.
- `listEmployeeBookings`: validates the employee and loads upcoming confirmed bookings ordered by start time.

### Room service operations

- Find active rooms whose capacity meets a minimum.
- Return a validated room entity for a given room identifier and participant count.

### Repositories and infrastructure

- Load and persist bookings.
- Test for overlapping confirmed bookings.
- Load the minimal employee reference.
- Obtain the current time through an injected clock.

Service transaction boundaries surround booking creation. Controllers do not start transactions or access repositories. They accept request DTOs and return response DTOs directly; Jackson owns JSON deserialization and serialization. Repository interfaces are Spring Data persistence contracts rather than application ports, and required JPA relations are fetched explicitly rather than globally eager.

## 10. Browser experience

The React/TypeScript application presents one focused demonstration journey:

1. A visible banner states that the application is a local demo using a fixed employee and has no authentication.
2. The booking form requests date, start time, end time, and participant count.
3. Submitting the form shows matching rooms ordered by capacity and name.
4. The user selects a room and confirms the booking.
5. A successful confirmation displays the room and interval and refreshes the `My bookings` section.
6. A conflict keeps the entered values, explains that availability changed, and offers a new search.

The interface must be responsive and keyboard accessible. Every request has explicit loading, empty, success, validation-error, and unexpected-error states. The timezone is shown as `Europe/Moscow`. Components use the typed API client and do not call `fetch` directly.

## 11. Acceptance scenarios

### AC-01: Find capacity-matching rooms

Given active rooms of capacities 4, 8, and 12 with no bookings, when the employee searches for 6 participants in a valid interval, then only the 8- and 12-person rooms are returned in ascending capacity order.

### AC-02: Exclude an occupied room

Given a confirmed booking from 10:00 to 11:00, when availability is requested from 10:30 to 11:30 for the same room, then that room is not returned.

### AC-03: Allow adjacent intervals

Given a confirmed booking from 10:00 to 11:00, when the room is booked from 11:00 to 11:30, then the new booking is confirmed.

### AC-04: Create and display a booking

Given a valid future interval and an available suitable room, when the demonstration employee confirms it, then the API returns `201`, the UI shows confirmation, and the booking appears immediately in `My bookings`.

### AC-05: Reject concurrent overlap

Given one available room, when two transactions concurrently create overlapping bookings for it, then exactly one succeeds and exactly one returns `BOOKING_CONFLICT`; only one record is persisted.

### AC-06: Recover from stale availability

Given a room was shown as available but another booking wins before confirmation, when the employee confirms, then the UI shows a recoverable conflict and retains the search input.

### AC-07: Reject invalid interval order

Given `start >= end`, when availability is searched or booking is attempted, then the API returns `400` with a field violation and no booking is written.

### AC-08: Reject invalid duration or increment

Given a duration under 30 minutes, over 4 hours, or a boundary not aligned to 30 minutes, when a request is made, then the API returns `400` with a stable validation code.

### AC-09: Reject outside working hours or booking horizon

Given an interval outside 08:00-22:00, in the past, crossing an office-local date, or starting more than 30 days ahead, when a request is made, then the API returns `400` and no booking is written.

### AC-10: Reject invalid room selection

Given an unknown room, an inactive room, or insufficient capacity, when booking is attempted, then the API returns the specified `404` or `400` outcome and no booking is written.

### AC-11: Reject invalid employee

Given an unknown employee identifier, when booking creation or list retrieval is attempted, then the API returns `404` and no booking is written.

### AC-12: Show an empty booking list

Given the demonstration employee has no upcoming bookings, when their list is opened, then the UI shows a useful empty state rather than an error.

### AC-13: Enforce layer boundaries

Given the backend source, when architecture tests run, then controllers do not access repositories or entities, DTOs are independent of persistence and service layers, repositories do not depend on web or service layers, and validators remain independent of HTTP and persistence.

### AC-14: Run the local vertical slice

Given a machine with Docker and Docker Compose, when the documented startup command completes, then the web application, backend readiness endpoint, and migrated PostgreSQL database are healthy and the scripted browser journey succeeds.

## 15. Recovery and rollback

The first feature is local-only. Flyway migrations are immutable and are not rolled back in place. Before public release exists, recovery is performed by stopping the local stack, recreating the project database, and replaying accepted migrations and seed data. Code rollback uses version control. Any future production deployment requires a separate release and data-migration plan.
